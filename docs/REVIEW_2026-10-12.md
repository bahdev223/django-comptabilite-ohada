## Correctifs de cette intervention

- Ligne→écriture : PROTECT, migration additive 0006, aucune migration 0001–0005 modifiée.
  Régression : même le collecteur ORM de base ne supprime plus les lignes en cascade.
- Les chemins secondaires EcritureService de clôture et amortissement refusent
  immédiatement les appels, comme les services métier déjà suspendus.
- Un ajout de ligne refuse un compte devenu inactif, après relecture sous les verrous existants.
- Le dashboard exclut les graphes journal/exercice/ligne appartenant à un autre
  tenant ; totaux de journaux limités aux écritures validées.
- Balance, grand livre, résultats et synthèse filtrent l'exercice explicite par FK,
  en plus des dates. Les exercices historiques qui se chevauchent ne sont pas mélangés.
- Sélection automatique d'exercice : refus si plusieurs périodes ouvertes couvrent la date.
- Contrepassation entre exercices : contrôle du tenant des deux périodes et
  verrouillage dans l'ordre des PK pour limiter les interblocages inverses.
  Original validé conservé, motif et référence stable, répétition refusée.
- Migration de conservation : restauration du schéma le plus récent à la fin du test.

## Limites et décision

NO-GO fusion/activation. Le package n'est pas certifié SYSCOHADA. Clôture,
réouverture, amortissements, rapprochements, anciennes API et signaux
django-comptes restent suspendus. Les helpers sectoriels (paie, TVA, stock,
trésorerie) nécessitent une revue d'imputation métier ; aucun raccordement automatique.
L'idempotence de référence ne remplace pas une inbox métier ; le signal on_commit
ne remplace pas une outbox durable. Les gardes ORM ne sont pas des triggers SQL
d'immutabilité ni une protection contre un administrateur utilisant du SQL brut.
Les écritures historiques sans tenant sont conservées et non réattribuées.

Exécuter PostgreSQL 16, migrations/rollback/restore, revue métier et contrats
Accounts/Platform avant décision de fusion. Aucun main, release, production,
Coolify ni application mobile modifié.
